# Full official Linux 4.19.191 filesystem experiment

Target: Redmi Note 11S 4G / POCO M4 Pro 4G (fleur, MT6781).

This is an isolated experiment based on Fleux Linux 4.19.325. It replaces the complete `fs/` directory with the official Xiaomi MT6781 Linux 4.19.191 `fs/` tree pinned to commit `6f6b84e0e2fa8d474db66798a051ec1835257729`. The matching official `include/linux/f2fs_fs.h` and `include/trace/events/f2fs.h` are also copied so the F2FS on-disk and trace definitions stay aligned with that donor.

The replacement includes VFS core files, mount/remount handling, F2FS, EXT4, FUSE, OverlayFS, FAT-family filesystems, and the other files under `fs/`. In the official 4.19.191 donor, EROFS still lives under `drivers/staging/erofs`, not under `fs/erofs`; the experiment therefore also imports that complete official EROFS source tree, its `include/trace/events/erofs.h` header, and merges only the EROFS Kconfig/Makefile registration lines into Fleux's existing staging files. Imported EROFS files are byte-verified against the pinned donor. It deliberately does not merge Fleux's newer filesystem-specific changes back into the replaced `fs/` directory. The MT6781 DPMAIF suspend/resume guard is in `drivers/` and is kept separately. Because replacing all of `fs/` also removes Fleux's SUSFS core, the experiment keeps the dedicated `fs/susfs.c` implementation and its `obj-$(CONFIG_KSU_SUSFS) += susfs.o` Makefile entry, together with the unchanged `include/linux/susfs.h` v2.3.0 header. The donor's two EXT4 fault callbacks are also adapted in `fs/ext4/inode.c`, and their declarations in `fs/ext4/ext4.h` are updated to return `vm_fault_t`, matching the Fleux 4.19.325 MM callback API. The two EXT4 `__vmalloc()` calls in `fs/ext4/super.c` are also adapted from the old three-argument form to the two-argument Fleux API. EXT4's old `e_reusable` field accesses in `fs/ext4/xattr.c` are mapped to the newer `MBE_REUSABLE_B` flag in `mb_cache_entry.e_flags` using `set_bit()`, `test_bit()`, and `clear_bit()`. The original 4.19.191 files are byte-verified before these explicit compatibility overlays are applied.  The donor's `fs/kernfs/mount.c` lookup helper is adjusted to Fleux 4.19.325's packed `u64` kernfs ID (`generation:ino`) API, using the existing `kernfs_id_ino()`, `kernfs_id_gen()`, and `kernfs_gen()` accessors; the generation check is retained. The FUSE inode also receives a local `VM_MAX_READAHEAD=128` KiB fallback because Fleux 4.19.325 no longer exports that legacy MM macro; this preserves the official FUSE readahead limit without changing the global MM header. It then reapplies only the four FleuxSU inline-hook sites required by its build-time checker: `ksu_handle_execveat`, `ksu_handle_faccessat`, `ksu_handle_sys_read`, and `ksu_handle_stat`. Their source locations and SUSFS guards are checked by the post-build audit; VFS/F2FS and the other filesystem implementation files remain from the pinned Xiaomi donor.

## Important compatibility impact

This creates a mixed-version kernel: Fleux 4.19.325 outside `fs/`, with the official 4.19.191 implementation inside `fs/`. The official donor predates Fleux's newer `fs_context` VFS path and filesystem-specific KernelSU/Fleux changes. Replacing the tree may therefore cause compile/link incompatibilities or remove filesystem-side hooks. The build is intentionally isolated on this branch and published only as a prerelease candidate.

The workflow must pass source-tree identity checks, compile the full kernel, verify the gzip kernel plus appended DTB, and validate the AnyKernel3 ZIP before publishing. A successful CI build still cannot establish that HyperOS can mount and decrypt real `/data`, access all existing files, preserve app data, or behave correctly across reboot and suspend/resume.

Do not overwrite the known-good kernel or remove the recovery path. Flash only after the image is built successfully and keep the previous boot image available. If the phone cannot mount userdata or reports filesystem errors, restore the known-good boot image; do not format userdata.
